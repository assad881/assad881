# كسّارة إكسبرس — منصة توريد ونقل مواد الكسارات

> **الاسم مؤقت.** يُغيَّر من مكان واحد: `config/app.config.js` → `brand.name`.

منصة وسيطة تربط **العميل** بـ **المورد (الكسارة)** و**الناقل**، تحت إشراف **إدارة المنصة**.
المنصة لا تملك كسارة ولا شاحنات؛ تنظّم الطلب والتسعير والدفع والتوريد والنقل مقابل رسوم وعمولة معلنة.

**التشغيل التجريبي:** ولاية عبري ومحافظة الظاهرة (عبري، ضنك، ينقل) — قابل للتوسّع دون تعديل كود.

> ⚠️ جميع البيانات في هذه النسخة (الموردون، الشاحنات، الأسعار، العملاء) **افتراضية وغير حقيقية**.

---

## 1. التشغيل

النسخة الحالية تعمل بلا خادم ولا حزم npm.

```bash
# الأسهل — انقر نقرًا مزدوجًا على index.html

# مع دعم PWA والعمل دون اتصال:
cd kassara && python3 -m http.server 8080   # ثم افتح http://localhost:8080
```

**حسابات العرض** (رمز التحقق دائمًا `1234`):

| الدور | الرقم |
|---|---|
| مدير النظام | `96899000001` |
| موظف عمليات | `96899000002` |
| عميل (فرد) | `96890000001` |
| عميل (شركة، شراء آجل) | `96890000002` |
| مقاول | `96890000003` |
| مورد — كسارة وادي الظاهرة | `96891000001` |
| شركة نقل — نقليات الظاهرة | `96892000001` |
| سائق | `96893000001` |

**الاختبار الذاتي:** افتح `index.html?selftest=1` — 52 اختبارًا يغطي التسعير ودورة الطلب والدفع
والاسترداد والصلاحيات وسلامة البيانات.

## 2. البنية

```
kassara/
├── index.html                 صفحة واحدة + موجّه hash
├── config/app.config.js       الهوية، العملة، الرسوم، طبقة البيانات، طرق الدفع
├── db/                        PostgreSQL: المخطط + RLS + دوال المعاملات
├── assets/css/app.css         نظام التصميم (كحلي/برتقالي/رملي، RTL، وضع داكن)
└── src/
    ├── core/                  util · i18n · store · router · auth (RBAC) · audit
    ├── data/                  schema · repo (واجهة موحّدة) · driver.local · driver.supabase · seed
    ├── domain/                pricing · orders · payments · trips · settlements · notify · analytics
    ├── ui/                    components · charts · layout · views/{public,auth,customer,admin,admin-config,partners}
    ├── selftest.js            اختبارات السيناريوهات والصلاحيات
    └── app.js                 المسارات + حارس الصلاحيات + الإقلاع
```

**فصل الطبقات:** الواجهة لا تلمس التخزين مطلقًا. كل قراءة وكتابة تمرّ عبر `KX.repo`،
وهو يوجّه إلى `driver.local` (تجريبي) أو `driver.supabase` (إنتاج) بنفس التوقيع تمامًا.

### الانتقال إلى PostgreSQL/Supabase

1. نفّذ `db/001_schema.sql` ثم `db/002_rls.sql` ثم `db/003_functions.sql`.
2. أضف `<script src="https://cdn.jsdelivr.net/npm/@supabase/supabase-js@2"></script>` في `index.html`.
3. في `config/app.config.js`: `data.driver = 'supabase'` مع `url` و`anonKey`.

لا يتغيّر أي سطر في `domain/` أو `ui/`.

## 3. الأدوار والصلاحيات

| الدور | الصلاحية |
|---|---|
| **العميل** | إنشاء الطلبات، الدفع، متابعة الشاحنات، تأكيد الاستلام، الفواتير، التقييم، الشكاوى |
| **المورد** | أسعاره وتوفّره، قبول الطلب أو طلب تعديله، تسجيل الكمية الفعلية وتذكرة الميزان، مستحقاته |
| **الناقل** | الشاحنات والسائقون، قبول المهمة، تعيين السائق، تحديث الحالات، رسوم الانتظار، مستحقاته |
| **السائق** | شاشة مهام مبسّطة بلا بيانات مالية، فتح الخرائط، تحديث الحالة، إثبات التسليم برمز العميل |
| **موظف عمليات** | متابعة الطلبات والتعيين والتحقق من التحويلات والشكاوى |
| **مدير النظام** | كل ما سبق + الأسعار والمناطق والعمولات والاستردادات والتقارير وسجل التدقيق |

الصلاحيات معرّفة في `src/data/schema.js` (`PERMISSIONS`)، ويطبّقها حارس المسارات في `src/app.js`
وفحص `KX.auth.can()` داخل الواجهات، وسياسات RLS في قاعدة البيانات.

## 4. معادلة السعر

```
سعر المواد  = الأطنان × سعر الطن (شريحة الكمية أو السعر التعاقدي إن وُجد)
تكلفة النقل = عدد الرحلات × (سعر الرحلة للمنطقة + سعر الكيلومتر × المسافة)
عدد الرحلات = ⌈ الأطنان ÷ حمولة الشاحنة ⌉
رسوم المنصة = رسم ثابت + نسبة × (المواد + النقل)
─────────────────────────────────────────────
السعر النهائي = (المواد + النقل + الرسوم − الخصم) + الضريبة
```

**ثوابت التصميم:**
- كل مكوّنات السعر تُعرض للعميل قبل الاعتماد.
- لكل طلب **لقطة سعر** (`price_snapshot`) محفوظة؛ تغيير قائمة الأسعار لاحقًا لا يمسّ الطلبات السابقة.
- توزيع الاستحقاق يُحسب مع السعر: `مستحق المورد + عمولته = قيمة المواد`، والمثل للناقل.
- لا تُثبَّت أي مادة أو سعر أو منطقة داخل الكود — كلها في قاعدة البيانات وتُدار من لوحة الإدارة.

## 5. حالات الطلب

```
مسودة → قيد المراجعة → بانتظار تأكيد المورد → بانتظار تعيين ناقل → جاهز للدفع
      → [بانتظار التحقق من التحويل] → مدفوع → قيد التجهيز → قيد التحميل
      → في الطريق → وصل إلى الموقع → تم التسليم
مسارات جانبية: ملغي · تحت المراجعة · مسترد جزئيًا · مسترد بالكامل
```

آلة الحالات في `src/domain/orders.js`: كل انتقال يحدّد **من أي حالة، إلى أي حالة، ولأي دور**.
أي انتقال خارج الجدول يُرفض برسالة واضحة. حارس إضافي: **لا تجهيز ولا تحميل قبل اكتمال السداد**.

## 6. سياسة الدفع

**لا يوجد دفع عند الاستلام إطلاقًا** (`payments.codEnabled = false`).

| الطريقة | الآلية |
|---|---|
| دفع إلكتروني | عبر طبقة `gateway` مجرّدة — يُربط مزوّد عُماني مرخّص دون تعديل منطق الأعمال |
| تحويل بنكي مسبق | يرفع العميل المرجع، وتعتمده الإدارة قبل الانتقال إلى «مدفوع» |
| عربون | نسبة مقدّمة، ويُسدَّد المتبقي قبل إصدار أمر التحميل |
| شراء آجل | للعملاء المعتمدين فقط ضمن حد ائتماني تحدده الإدارة |

**لا تُخزَّن بيانات البطاقات** — آخر أربعة أرقام ومرجع العملية فقط.
**منع الدفع المزدوج** عبر `idempotency_key` فريد لكل محاولة (وقفل صف `FOR UPDATE` في نسخة PostgreSQL).

## 7. المرحلة القادمة

| البند | الحالة |
|---|---|
| الواجهات والتسعير ودورة الطلب والدفع التجريبي والفواتير والتسويات | ✅ مكتمل |
| لوحات العميل والمورد والناقل والسائق والإدارة | ✅ مكتمل |
| مخطط PostgreSQL + RLS + دوال المعاملات | ✅ مكتوب وجاهز للتنفيذ |
| ربط Supabase فعليًا (نقل البيانات وتفعيل Auth) | ⏳ يحتاج مشروع Supabase |
| بوابة دفع عُمانية مرخّصة | ⏳ يحتاج تعاقدًا — الطبقة جاهزة |
| SMS / واتساب / بريد / Push | ⏳ معطّلة في `domain/notify.js` حتى ربط مزوّد |
| خريطة تفاعلية لاختيار الموقع | ⏳ حاليًا إحداثيات + زر «موقعي الحالي» |
| تتبّع مباشر للشاحنة (GPS) | ⏳ حاليًا حالات يدوية من السائق |
| تطبيقات iOS/Android | ⏳ PWA جاهز — يُغلَّف بـ Capacitor لاحقًا |
